# ElevMan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build ElevMan v1, an offline Android app for managing elevator manuals, error codes, maintenance tasks and service history, with zip backups for sharing between phones.

**Architecture:** Kotlin and Jetpack Compose over a Room (SQLite) database, with PDFs in app-private storage. Rules (code normalization, due dates, suggestion parsing, merge planning) are pure Kotlin so they test on the JVM. Storage and PDF work sit behind small interfaces so tests can substitute fakes.

**Tech Stack:** Kotlin, Jetpack Compose (Material 3), Room with KSP, kotlinx.serialization, `java.time`, PdfBox-Android (`com.tom-roush:pdfbox-android`) for text extraction, Android `PdfRenderer` for display, JUnit 4, Robolectric for Room tests, Compose UI test for screens.

**Spec:** `docs/superpowers/specs/2026-10-15-elevman-design.md`

## Global Constraints

- Android 10 or later: `minSdk = 29`.
- Offline: the app declares no `INTERNET` permission. No PDF or record leaves the phone.
- Every record has a string UUID `id` and an `updatedAt` epoch-millisecond timestamp in UTC.
- Review statuses are exactly `SUGGESTED`, `CONFIRMED`, `REJECTED`.
- PDFs live at `filesDir/manuals/<manualId>.pdf`.
- Backup is a zip with `backup.json` (`"version": 1`) and `manuals/<manualId>.pdf` entries.
- Suggested items are labelled "Suggested" and never shown as confirmed.
- "Accept all" requires a confirm step that shows the count.
- Mark-done dates cannot be in the future.
- Commit at the end of each task on `claude/optimistic-dijkstra-qf5rsg`. Push the branch when the plan is complete.

## Decisions the spec left open

The spec's wording is unchanged. These are the choices the plan makes.

- **Due date:** `base + intervalMonths`, where `base` is the last completed date, or the date the task was added to the elevator if it was never completed. Month arithmetic uses `LocalDate.plusMonths`.
- **Merge tie:** same `id`, same `updatedAt`, different content: the local version is kept and the incoming version is listed as overridden.
- **Search:** exact match on the normalized code (Task 3).
- **Accept all:** applies to the suggested items of the one manual under review.
- **Maintenance extraction:** uses the keyword table in Task 7.
- **Cause and fix:** the parser fills only the meaning. Cause and fix are typed in during review.

## Review Focus

1. Spelling variants of a code ("e-21", "E 21", "E21") find the same code. Tests: Task 3, Task 10.
2. A scanned PDF with no text gives zero suggestions, a clear message, and no crash. Tests: Task 6, Task 8.
3. Importing the same PDF twice is skipped, and the message names the existing manual. Test: Task 5.
4. Due dates land on valid dates at month ends, and a never-completed task is due one interval after it was added. Test: Task 4.
5. A corrupt backup, or one with a missing PDF, changes nothing. Tests: Task 13, Task 14.

### Task 7: Suggestion parser

**Files:**
- Create: `app/src/main/java/com/elevman/pdf/SuggestionParser.kt`
- Test: `app/src/test/java/com/elevman/pdf/SuggestionParserTest.kt`

**Interfaces:**
- Consumes: `PageText` (Task 6).
- Produces:
  ```kotlin
  data class SuggestedCode(val code: String, val meaning: String, val pageNumber: Int)
  data class SuggestedTask(val name: String, val intervalMonths: Int, val pageNumber: Int)
  object SuggestionParser {
      fun errorCodes(pages: List<PageText>): List<SuggestedCode>
      fun maintenanceTasks(pages: List<PageText>): List<SuggestedTask>
  }
  ```

**Error code rule.** Split each page into lines and trim them. A line starts an entry when it matches `^([A-Z]{1,4}[- ]?[0-9]{1,4}[A-Z]?)\s+(\S.*)$`. `code` is group 1 exactly as printed, so it is not normalized. `meaning` is group 2, followed by the following lines that do not start an entry, joined with a single space. A blank line or the next matching line ends the entry.

**Maintenance rule.** A line is a task when it contains a keyword, matched case-insensitively. The table is checked in order, and the first match wins:

| Keyword (in order) | `intervalMonths` |
|---|---|
| `semi-annual`, `six-monthly`, `every 6 months` | 6 |
| `quarterly` | 3 |
| `monthly` | 1 |
| `annual`, `yearly`, `every 12 months` | 12 |

`semi-annual` comes before `annual` so that it does not match 12. `name` is the trimmed line.

- [ ] **Step 1: Write the failing tests:** `parsesCodeWithMeaning` (`E-21 Door interlock fault` gives code `E-21`, meaning `Door interlock fault`); `joinsContinuationLines` (`E-22 Overspeed` followed by `Check governor` gives meaning `Overspeed Check governor`); `blankLineEndsEntry`; `codeKeepsPrintedSpelling` (`E 21 Fault` gives code `E 21`); `ignoresLinesThatDoNotStartWithCode` (`12 Hoist motor` and `e-21 lower` give nothing); `maintenanceKeywordTable` (`Monthly: inspect door locks` gives 1, `Semi-annual lubrication` gives 6, `Yearly safety test` gives 12, `Inspect the pit` gives no task).

  ```kotlin
  data class Overridden(val table: String, val id: String, val label: String, val winner: Side)
  data class MergePlan(val added: Int, val updated: Int, val overridden: List<Overridden>)
  object MergePlanner {
      fun plan(local: BackupDocument, incoming: BackupDocument): MergePlan
  }
  class BackupApplier(
      db: ElevManDatabase,
      filesDir: File,
      copyPdf: (from: File, to: File) -> Unit = { a, b -> a.copyTo(b) },
      onWrite: (table: String) -> Unit = {},
  ) {
      suspend fun apply(valid: ReadResult.Valid, plan: MergePlan)   // uses valid.document as the incoming side
  }
  ```

**Planner rules.** Match records by table and `id`. An incoming id that is not local counts as `added`. For an id present on both sides with identical content, nothing happens. For different content, a greater incoming `updatedAt` makes the incoming side win and counts as `updated`. Otherwise the local side wins, including on a tie, and the incoming version is listed in `overridden`. When incoming wins, the local version is listed in `overridden` as well. Local-only records are kept.

**Applier rules.** Copy the PDFs for added or updated manuals from staging into `filesDir/manuals/`. Then write all winning rows in one Room transaction, calling `onWrite(table)` before each table's upsert. If anything throws, delete the copied PDFs and rethrow, which rolls back the transaction.
